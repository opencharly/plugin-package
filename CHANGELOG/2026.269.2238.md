# 2026.269.2238 — feat(package)!: own the typed-step kind + materialization (C7)

## Summary

C7 crutch-sweep, producer-first leg 4/5. Adopt `sdk` `v0.2026269.2222` (which adopts
`spec#177`, `v0.2026269.2150`): the `package` verb candy now **owns both halves** of its
typed install-step lowering, so charly core holds no per-kind switch.

Before this PR the candy returned a neutral `kit.StepDescriptor` + a candy-local
`kit.StepKindName`, and charly's `check_kit_adapter.go` mapped the kind
(`kitStepKindToCharly`) and rebuilt the real step (`materializeStep`) — a kernel kind switch,
an incomplete seam by the boundary law. Now the candy implements the widened
`checkstep.StepProvider`:

```go
func (verb) StepKind() spec.StepKind { return spec.StepKindSystemPackages }

func (verb) MaterializeStep(op *spec.Op, _, _ string, pkgFormat string, distroTags []string) spec.InstallStep {
	var in params.PackageInput
	kit.DecodeInput(op.PluginInput, &in)
	return &spec.SystemPackagesStep{
		Format:   pkgFormat,
		Phase:    spec.PhaseInstall,
		Packages: []string{kit.ResolvePackageName(in.Package, in.PackageMap, distroTags)},
	}
}
```

The load-bearing `Reverse()` (package-remove) stays on the built step (package main) — the
candy owns only the construction. `ConstructStepDescriptor` and the descriptor types are gone;
`TestPackageVerb_StepProvider` now asserts the real `*spec.SystemPackagesStep`, including the
image `Format` + `PhaseInstall` and the cross-distro-resolved name from the `package_map`.

Also adds the missing `InvokeProvider` method to the test `fakeCC` — the newer SDK's
`CheckContext` requires it, and the pin bump surfaces the latent test staleness (R2, fixed
here).
